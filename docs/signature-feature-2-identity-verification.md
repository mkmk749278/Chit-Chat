# Signature Feature 2 — In-Chat Identity Verification (Rotating TOTP + Duress Code)

> Design + threat model. Source of truth: `private-chat-app-requirements.md` §4 (decision D6).
> Status: **crypto core + E2E wiring + mobile UI shipped**; persistent per-conversation seed and
> hardened duress-entry UX are tracked follow-ups (see _Limitations_).

## 1. Problem

End-to-end encryption verifies the **channel** and the **device keys** — not the **human** typing.
Anyone holding an unlocked device can message as the owner. This feature lets either party run an
in-chat challenge that confirms the responder holds the conversation's shared verification secret,
with a second "duress" answer that is indistinguishable to an observer but lets the responder's app
fire a silent alert to a trusted contact (§4.1–§4.3).

## 2. Cryptographic construction

Implemented in `packages/crypto/src/identity-verification.ts` (pure WebCrypto; no I/O; shipped
byte-for-byte to web and mobile, Requirement C2).

- **Verification seed** — a 32-byte secret. It is generated by the requester, shared over the
  existing E2E channel (never to the server), and held by both peers. From one seed two independent
  HMAC sub-keys are derived by domain separation so the normal and duress streams are unlinkable:
  - `normalKey = HMAC-SHA256(seed, "chit-chat/identity-verify/normal/v1")`
  - `duressKey = HMAC-SHA256(seed, "chit-chat/identity-verify/duress/v1")`
- **Rotating code** — each stream is a standard **RFC 6238 TOTP** (= RFC 4226 HOTP over HMAC-SHA1)
  of its sub-key with a **60-second** time step (`VERIFICATION_STEP_SECONDS`), 6 digits. The valid
  answer rotates every 60 s and a captured code cannot be replayed in a later step (§4.2). The HOTP
  primitive is checked directly against the **RFC 4226 Appendix-D test vectors**.
- **Verification** — `classifyVerificationCode(seed, code, now)` accepts the current step ±1 (clock
  skew / read-out latency, RFC 6238 §5.2) and returns `normal | duress | invalid`. Duress takes
  priority on the astronomically rare step where both 6-digit streams coincide, so a genuine duress
  answer is never silently downgraded — the safety of the person under duress is favoured.

## 3. Protocol (over the E2E content payload)

The challenge rides inside the existing libsignal ciphertext as new
`content-payload.ts` variants, so the **server never learns a verification is happening** (the wire
frame carries only an opaque `CiphertextEnvelope`):

| Payload | Direction | Meaning |
|---|---|---|
| `verify-request{seed}` | requester → responder | start; carries the fresh base64 session seed |
| `verify-response{code}` | responder → requester | the rotating code the responder submitted |
| `verify-result{ok}` | requester → responder | outcome, so both badges converge (§4.3) |
| `duress-alert{peerUid}` | responder → trusted contact | silent alert; no content |

`Messaging` exposes `requestVerification`, `respondVerification(kind, trustedContactUid?)`, and
`onVerification(...)`; the mobile `ChatController` and `ConversationScreen` surface the per-session
badge (`Verified ✓` / `Unverified` / pending) and the duress-capable response sheet.

Pass/fail behaviour matches §4.3: a normal **or** duress code reads as a pass to the requester
(indistinguishable); any duress side-effect (the silent alert) fires on the responder's device.

## 4. Threat model

| Threat | Mitigation |
|---|---|
| Impostor on an unlocked device messaging as the owner | The challenge confirms possession of the shared verification secret; the per-session badge tells the peer whether the human was confirmed. |
| Replay of a captured code | 60 s rotation + bounded ±1-step acceptance window; a code is dead two steps later (tested). |
| Server learns a verification / its codes | Seed and codes ride **inside** the E2E ciphertext; the relay sees only an opaque envelope (tested: no `verify-*` markers on the wire). |
| Coercion (someone forces the user to verify) | Duress code: passes identically to an observer, silently alerts a pre-configured trusted contact over the encrypted channel — **never** via SMS or Call Log (Restricted Permissions this app does not request, §4.2). |
| Verification state surviving the session | Seeds are RAM-only and cleared on `dispose` (app lock/exit); badge state resets per session (§4.4). |

## 5. Limitations / follow-ups

- **Session-scoped seed (v1).** The seed is generated per verification request and held in RAM,
  which satisfies §4.4 ("state resets on app lock/exit") and the ephemeral-by-construction posture,
  but defers §4.2's "seed exchanged at conversation initiation, stored encrypted". A persistent
  per-conversation seed (new `KeyStore` method + encrypted vault entry) is a follow-up so a stable
  duress code is recallable across sessions.
- **Duress-entry UX hardening.** The current sheet exposes an explicit "send under duress" action.
  A discreet gesture / disguised affordance (so the duress path is unobservable even on-screen) is a
  follow-up to be defined alongside the persistent-seed work.
- **"No response within 2 min → Identity unconfirmed"** (§4.3) timeout badge is a small UI follow-up.
