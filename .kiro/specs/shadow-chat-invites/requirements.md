# Requirements Document

## Introduction

This document specifies the requirements for **Shadow Chat Invites**, an evolution of the
already-shipped Shadow Chat feature. It is **derived from** the approved design at
[`.kiro/specs/shadow-chat-invites/design.md`](./design.md), which is the authoritative source for the
technical approach; every requirement below traces to a behaviour, decision, or correctness property
stated there.

The feature changes exactly one thing about how a shadow thread comes to exist: instead of being a
silent, local-only, single-device construct reached by typing a private `/alias`, a shadow thread
becomes a **two-party, invitation-based** construct with **explicit consent** and a **recipient
routing choice**. In doing so it fixes a fatal two-party defect in the shipped implementation: the
inviter and recipient previously derived **different** `threadId`s for the "same" conversation
because the HMAC key (`shadowMasterSecret`) was a device-local value that was never transmitted, so
inbound shadow messages were rejected with `UnknownShadowThreadError`. The fix establishes a
**shared per-thread key** carried encrypted inside the existing E2E channel so both sides converge on
an identical `threadId`.

The feature also adds strict shadow-message delivery, a local "Clear shadow chat" history purge, a
two-sided "Revoke shadow chat" teardown, and automatic cleanup of transient invite-control traffic —
all while preserving the **frozen backend** (no wire/envelope/ack/codec change), decoy/locked
inertness, and the inviter's surface-chat invariants, and remaining backward compatible with legacy
alias-only threads.

## Glossary

- **Shadow_Thread**: A two-party parallel conversation that is isolated from the surface chat, has its
  own `ConversationState` and `+1e9` sequence space, and (by default) is excluded from the chat list
  and notifications.
- **threadId**: The 64-character lowercase-hex HMAC-SHA256 identifier of a Shadow_Thread, computed as
  `deriveShadowThreadId(threadKey, uidA, uidB)`. For invited threads it is derived with **no alias
  discriminator** and is **never transmitted on the wire**.
- **threadKey (shared per-thread key)**: A fresh 32-byte CSPRNG value, generated by the inviter,
  carried encrypted inside the `shadow-invite` payload, and held by **both** peers. It is the HMAC key
  for an invited thread's `threadId`. Each side stores its own wrapped copy in its own encrypted
  vault; it is never re-transmitted after Accept.
- **Surface_Chat**: The normal (non-shadow) conversation between two real UIDs, identified by
  `surface:${peerUid}`.
- **Invite_Control_Payload**: One of the encrypted control messages `shadow-invite`, `shadow-accept`,
  `shadow-decline`, or `shadow-revoke`, intercepted before conversation routing and never rendered as
  an ordinary conversation row.
- **shadow-invite**: Inviter → recipient control payload `{ inviteId, key, label? }` that opens a
  two-party shadow thread; carries the shared 32-byte `threadKey` (base64).
- **shadow-accept**: Recipient → inviter control payload `{ inviteId }` signalling acceptance; the
  routing choice stays local to the recipient.
- **shadow-decline**: Recipient → inviter control payload `{ inviteId }` signalling refusal.
- **shadow-revoke**: Either-peer → other control payload `{ inviteId, threadId }` instructing the peer
  to delete the shared key + that thread's local history and close the thread; carries no key and no
  content.
- **Recipient_Routing**: The recipient's Accept-time choice of `hidden` (default — a hidden shadow
  thread) or `merge` (surface the thread in the recipient's main chat, view-only).
- **Real_Mode / Decoy_Mode / Locked_Mode**: Application modes resolved by App-Lock. Real_Mode unlocks
  shadow context; Decoy_Mode and Locked_Mode (collectively "null" mode for shadow purposes) release no
  shadow context and behave inertly.
- **InvitedThreadRecord**: The device-local, encrypted-at-rest record for an invited thread holding
  `inviteId`, `peerUid`, `threadId`, `threadKey`, `routing`, `state`, optional `alias`, optional
  `pinVerifier`, and `createdAt`.
- **ShadowInviteCoordinator**: The pure-core component owning the invite/accept/decline/revoke
  lifecycle, emitting `ShadowInviteEvent`s, and performing invite-control auto-cleanup.
- **ShadowSecretStore**: The pure-core component persisting invited-thread secrets and mappings (it
  does not hold messages).
- **ShadowSecretPersistence**: The narrow injected port backing `ShadowSecretStore` with the encrypted
  vault.
- **ConversationRegistry**: The pure-core component that isolates per-thread `ConversationState`,
  routes inbound events by `threadId`, and controls chat-list/notification visibility.
- **ContentPayloadCodec**: The `content-payload.ts` encoder/decoder; decoding is **total** and unknown
  payload types decode to `{ type: 'unsupported' }`.
- **Messaging**: The pure-core component that decrypts inbound envelopes, decodes content payloads,
  and intercepts control payloads before conversation routing.
- **KeyStore.purgeMessages**: The existing local message-history purge primitive, reused by both
  "Clear chat" and the new "Clear/Revoke shadow chat" actions.
- **Row_Thread_Association**: A device-local, additive mapping from persisted message rows to their
  `threadId`, enabling per-`threadId` history purges (the persisted `MessageRow` has no `threadId`
  today).
- **Pre_Accept_Queue**: The inviter's local, untransmitted queue of messages typed into an
  `awaiting-accept` thread before the recipient Accepts.
- **Frozen_Backend**: The deployed backend at `api.luminchat.app`, which must not change; all shadow
  behaviour rides inside the existing E2E ciphertext as ordinary `CiphertextEnvelope`s.
- **CiphertextEnvelope**: The existing opaque wire frame between two real UIDs.

## Requirements

### Requirement 1: Visible invite from a contact long-press

**User Story:** As an inviter, I want to start a shadow chat by long-pressing a contact, so that the
recipient receives an explicit, consent-based request in their main chat.

#### Acceptance Criteria

1. WHILE App_Mode is Real_Mode, WHEN the inviter long-presses a contact and selects "Shadow chat", THE ShadowInviteCoordinator SHALL create an invite for that contact's `peerUid`.
2. WHEN the ShadowInviteCoordinator creates an invite, THE ShadowInviteCoordinator SHALL send exactly one `shadow-invite` control payload to the recipient over the existing E2E channel.
3. WHEN a recipient device receives a `shadow-invite` control payload in Real_Mode, THE ShadowInviteCoordinator SHALL emit an `invite-received` event that renders an Accept/Decline request card in the recipient's Surface_Chat with that `peerUid`.
4. THE ShadowInviteCoordinator SHALL treat each shadow chat as its own separate invite, such that every follow-up invite request arrives in the recipient's Surface_Chat and never nested inside a previously created Shadow_Thread.
5. WHILE App_Mode is Decoy_Mode or Locked_Mode, WHEN the inviter views the contact long-press menu, THE long-press menu SHALL omit the "Shadow chat" option.
6. WHEN the ShadowInviteCoordinator creates and sends an invite, THE inviter's `surface:${peerUid}` ConversationState SHALL remain identical to its value had no invite occurred.

### Requirement 2: Shared-key rendezvous and threadId convergence (core fix)

**User Story:** As a shadow-chat participant, I want both sides to derive the same threadId on Accept, so that shadow messages converge instead of being rejected as an unknown thread.

#### Acceptance Criteria

1. WHEN the ShadowInviteCoordinator creates an invite, THE ShadowInviteCoordinator SHALL generate a fresh 32-byte `threadKey` from the injected cryptographic random source.
2. THE ShadowInviteCoordinator SHALL place the `threadKey` (base64-encoded) inside the encrypted `shadow-invite` payload and SHALL NOT transmit it outside the E2E ciphertext.
3. WHEN deriving an invited thread's `threadId`, THE ShadowSecretStore SHALL compute `deriveShadowThreadId(threadKey, uidA, uidB)` using only the shared `threadKey` and the UID pair, with no alias discriminator.
4. FOR ALL 32-byte `threadKey` values and all distinct non-empty UIDs `uidA` and `uidB`, THE ShadowSecretStore SHALL derive a `threadId` such that `deriveShadowThreadId(threadKey, uidA, uidB)` equals `deriveShadowThreadId(threadKey, uidB, uidA)`.
5. WHEN an invite is created and then accepted, THE ShadowSecretStore SHALL cause the inviter's stored `threadId` to equal the recipient's stored `threadId`.
6. WHEN each side stores the `threadKey`, THE ShadowSecretStore SHALL wrap and persist that side's own copy in that side's own encrypted vault and SHALL NOT re-transmit the `threadKey` after Accept.
7. FOR ALL pairs of distinct `threadKey` values applied to the same UID pair, THE ShadowSecretStore SHALL derive distinct `threadId` values with overwhelming probability.
8. WHEN binding an invited thread, THE ShadowSecretStore SHALL recompute `threadId` from the stored `threadKey` rather than trusting any transmitted identifier.

### Requirement 3: Recipient routing choice on Accept

**User Story:** As a recipient, I want to choose whether an accepted shadow chat stays hidden or merges into my main chat, so that I control the privacy/convenience trade-off on my own device.

#### Acceptance Criteria

1. WHEN the recipient taps Accept, THE routing-choice sheet SHALL offer `hidden` and `merge` options with `hidden` as the default.
2. WHEN the recipient accepts with `routing = 'hidden'`, THE ConversationRegistry SHALL open the Shadow_Thread excluded from `listSurfaceConversations()` and non-notifiable.
3. WHEN the recipient accepts with `routing = 'merge'`, THE ConversationRegistry SHALL mark the Shadow_Thread surface-visible so it appears in `listSurfaceConversations()` under `peerUid` and is notifiable.
4. WHERE the recipient chose `merge`, THE ConversationRegistry SHALL keep the Shadow_Thread's own isolated ConversationState and `+1e9` sequence space unchanged and SHALL change only the chat-list view and notification policy.
5. WHEN the recipient accepts, THE ShadowInviteCoordinator SHALL send a `shadow-accept` control payload that does not encode the recipient's routing choice, so the inviter does not learn it.
6. THE ShadowInviteCoordinator SHALL keep the inviter's Recipient_Routing fixed at `hidden`, documenting the asymmetry that only the recipient may choose `merge`.

### Requirement 4: Strict delivery into the shadow thread only

**User Story:** As a shadow-chat participant, I want shadow messages to be delivered only after Accept and only into the shadow thread, so that no shadow content ever leaks into either side's main chat.

#### Acceptance Criteria

1. WHILE an invited thread state is `awaiting-accept`, WHEN the inviter types a message into that thread, THE ShadowInviteCoordinator SHALL append the message to the Pre_Accept_Queue locally and SHALL NOT transmit it.
2. WHEN the inviter receives a `shadow-accept`, THE ShadowInviteCoordinator SHALL flush every queued Pre_Accept_Queue message exactly once, in enqueue order, with strictly increasing contiguous shadow sequence numbers greater than or equal to `SHADOW_SEQ_OFFSET`.
3. IF the invite is declined or expires, THEN THE ShadowInviteCoordinator SHALL discard all Pre_Accept_Queue messages without transmitting them.
4. FOR ALL shadow messages and all Recipient_Routing values in {`hidden`, `merge`}, WHEN a shadow message is applied, THE ConversationRegistry SHALL mutate only the `shadow:${threadId}` ConversationState and SHALL NOT mutate `surface:${peerUid}` on either side.
5. THE ShadowInviteCoordinator SHALL NOT transmit any shadow message while its thread state is `awaiting-accept`.
6. WHERE the recipient chose `merge`, THE ConversationRegistry SHALL treat the merge as a view-only override and SHALL NOT change the thread membership of any shadow message.

### Requirement 5: Optional per-chat PIN

**User Story:** As a shadow-chat participant, I want to optionally protect a shadow chat with a per-chat PIN, so that I can add a second factor without changing existing behaviour.

#### Acceptance Criteria

1. WHERE a PIN is supplied at invite creation or at Accept, THE ShadowSecretStore SHALL store only a PIN verifier produced by `secret-hash.hashSecret` and SHALL NOT store the plaintext PIN.
2. WHERE no PIN is supplied, THE ShadowSecretStore SHALL bind the invited thread without a per-chat PIN.
3. THE ShadowSecretStore SHALL allow a per-chat PIN to be set at thread creation or later, preserving the shipped per-chat PIN behaviour unchanged.

### Requirement 6: Clear shadow chat (local history purge, keep key)

**User Story:** As a shadow-chat participant, I want to clear one shadow chat's local history while keeping the chat working, so that I can wipe history without re-inviting.

#### Acceptance Criteria

1. WHILE App_Mode is Real_Mode, WHEN the user selects "Clear shadow chat" for a `threadId`, THE ShadowSecretStore SHALL validate that an InvitedThreadRecord for `threadId` exists and SHALL keep the InvitedThreadRecord and its shared `threadKey` intact.
2. WHEN "Clear shadow chat" runs, THE KeyStore.purgeMessages primitive SHALL purge all message rows whose `threadId` matches, with row ids resolved through the Row_Thread_Association.
3. WHEN "Clear shadow chat" runs, THE ConversationRegistry SHALL reset the `shadow:${threadId}` ConversationState to empty, scoped to that thread only, leaving no tombstone and disturbing no other conversation.
4. WHEN a "Clear shadow chat" completes, THE ShadowSecretStore SHALL keep the thread routable such that a subsequent send or receive on the same `threadId` succeeds and routes to `shadow:${threadId}`.
5. THE ShadowInviteCoordinator SHALL NOT transmit any wire traffic for a "Clear shadow chat" action, leaving the peer's history untouched.
6. IF App_Mode is Decoy_Mode or Locked_Mode, THEN THE ShadowSecretStore SHALL treat "Clear shadow chat" as a no-op that reveals nothing.
7. THE ShadowSecretStore SHALL apply "Clear shadow chat" per shadow chat (one `threadId` at a time).

### Requirement 7: Revoke shadow chat (delete key + history on both sides)

**User Story:** As a shadow-chat participant, I want to revoke a shadow chat so that both sides delete the key and history and the thread becomes unusable, so that I can make a conversation unrecoverable.

#### Acceptance Criteria

1. WHILE App_Mode is Real_Mode, WHEN the user selects "Revoke shadow chat" for a `threadId`, THE ShadowInviteCoordinator SHALL purge the thread's local history via KeyStore.purgeMessages and SHALL atomically delete the shared `threadKey`, the InvitedThreadRecord, and any AliasEntry for that `threadId`.
2. WHEN the ShadowInviteCoordinator performs a local revoke deletion, THE ShadowInviteCoordinator SHALL persist the local deletion before sending the `shadow-revoke` payload and SHALL NOT require any peer acknowledgement (fail-closed, local-first).
3. WHEN local revoke deletion has been persisted, THE ShadowInviteCoordinator SHALL send exactly one `shadow-revoke` control payload carrying `inviteId` and `threadId` and no key and no content over the existing E2E channel.
4. WHEN a device receives a `shadow-revoke` for a known `threadId` in Real_Mode, THE ShadowInviteCoordinator SHALL purge that thread's local history, delete its shared `threadKey` and InvitedThreadRecord, close the thread in the ConversationRegistry, and emit `thread-revoked` with `initiatedBy = 'peer'`.
5. WHEN a revoke completes on a device, THE ShadowSecretStore SHALL leave no InvitedThreadRecord, no `threadKey`, and no AliasEntry for that `threadId`, so the `threadId` cannot be re-derived or reopened from persisted state.
6. IF a revoke is requested for an unknown or already-revoked `threadId`, THEN THE ShadowInviteCoordinator SHALL perform a total no-op that changes nothing and sends nothing.
7. IF App_Mode is Decoy_Mode or Locked_Mode, THEN THE ShadowInviteCoordinator SHALL treat both an outbound revoke request and an inbound `shadow-revoke` as a no-op that deletes nothing, touches no key, and sends nothing.
8. IF the atomic delete in ShadowSecretStore fails, THEN THE ShadowSecretStore SHALL abort by propagating the error, leaving the InvitedThreadRecord and `threadKey` intact with no partial deletion.
9. IF the socket is unavailable when sending `shadow-revoke`, THEN THE Messaging component SHALL retain the local deletion as already persisted and SHALL deliver the `shadow-revoke` via the existing pending-send flush-on-reconnect path.

### Requirement 8: Auto-cleanup of invite-control traffic

**User Story:** As a shadow-chat participant, I want invite-control residue to be removed automatically once an invite is resolved, so that no transient bookkeeping persists beyond what is needed.

#### Acceptance Criteria

1. WHEN an invite is accepted, THE ShadowInviteCoordinator SHALL delete the recipient's `shadow-invite` record and the visible request card and SHALL retain only the active InvitedThreadRecord on both sides.
2. WHEN an invite is declined, THE ShadowInviteCoordinator SHALL delete the recipient's `shadow-invite` record and request card and SHALL discard the inviter's pending InvitedThreadRecord, its `threadKey`, and its Pre_Accept_Queue messages, leaving no invite residue.
3. IF an invite receives no response within its expiry TTL, THEN THE ShadowInviteCoordinator SHALL, on each side independently, discard the pending record, its `threadKey`, and any Pre_Accept_Queue messages, leaving no invite residue.
4. WHEN an invite reaches a terminal state of accepted, declined, or expired, THE ShadowInviteCoordinator SHALL emit exactly one `invite-resolved` event with the corresponding reason.
5. WHEN an invite lifecycle ends, THE ShadowInviteCoordinator SHALL ensure the only persisted artefact is the active InvitedThreadRecord for an accepted invite, or nothing for a declined or expired invite.

### Requirement 9: Frozen-backend constraint

**User Story:** As a system architect, I want all new control traffic to ride inside existing ciphertext, so that the deployed backend remains frozen.

#### Acceptance Criteria

1. THE ShadowInviteCoordinator SHALL carry every `shadow-invite`, `shadow-accept`, `shadow-decline`, and `shadow-revoke` control payload inside the existing E2E libsignal ciphertext and SHALL NOT add any new endpoint, envelope field, ack frame, or codec change.
2. FOR ALL invite, accept, decline, and shadow messages, THE Messaging component SHALL produce a CiphertextEnvelope whose field set, count, types, and ordering match a Surface_Chat envelope between the same UIDs.
3. THE Messaging component SHALL ensure no `threadId` and no plaintext appears on the wire for any shadow control payload or shadow message.
4. FOR ALL `shadow-revoke` payloads, THE Messaging component SHALL produce a CiphertextEnvelope that contains no key, no plaintext, and no `threadId` on the wire, carrying the `threadId` reference only inside the ciphertext.
5. THE ContentPayloadCodec SHALL add the four shadow control types as additive discriminated variants without altering any existing variant.

### Requirement 10: Decoy/locked inertness and no-surface-disturbance

**User Story:** As a privacy-conscious user, I want shadow-invite behaviour to reveal nothing under coercion and to never disturb the inviter's surface chat, so that deniability is preserved.

#### Acceptance Criteria

1. WHILE App_Mode is Decoy_Mode or Locked_Mode, WHEN a `shadow-invite` arrives, THE ShadowInviteCoordinator SHALL silently ignore it, create no thread, and render no event that reveals an invite.
2. WHILE App_Mode is Decoy_Mode or Locked_Mode, WHEN `createInvite` or `acceptInvite` is called, THE ShadowInviteCoordinator SHALL return null, release no shadow context, and send nothing.
3. FOR ALL inbound invites and revoke actions, THE ShadowInviteCoordinator SHALL produce observable behaviour that is identical between Decoy_Mode and Locked_Mode within 50 milliseconds.
4. FOR ALL invite lifecycles including sent, accepted, declined, and expired with arbitrary Pre_Accept_Queue messages, THE ShadowInviteCoordinator SHALL keep the inviter's `surface:${peerUid}` ConversationState byte-for-byte identical to its value had no invite occurred.
5. THE ShadowInviteCoordinator SHALL surface the visible request card only as a UI rendering of the `invite-received` event attached to the surface contact and SHALL NOT insert a surface message row in the conversation reducer.

### Requirement 11: Backward compatibility with legacy alias-only threads

**User Story:** As an existing user, I want my legacy alias-only shadow threads to keep working without migration, so that upgrading does not break existing conversations.

#### Acceptance Criteria

1. FOR ALL legacy `bindAlias` inputs, THE ShadowSecretStore SHALL derive a `threadId` that is byte-for-byte identical before and after this feature, using the device-local `masterSecret` plus alias path.
2. THE ShadowSecretStore SHALL NOT rewrite or migrate any existing stored AliasEntry or derived `threadId`.
3. WHEN a peer that predates this feature receives a `shadow-invite`, `shadow-accept`, `shadow-decline`, or `shadow-revoke`, THE ContentPayloadCodec SHALL decode it to `{ type: 'unsupported' }` so the peer ignores it without crashing or losing data.
4. THE ShadowSecretStore SHALL keep the device-local `masterSecret` and `aliasKey` in place for alias hashing and for legacy alias-only threads, changing only the convergence key used for invited threads.

### Requirement 12: Total decode of inbound content payloads

**User Story:** As a shadow-chat participant, I want all inbound payloads to decode safely, so that malformed or unknown messages never crash the client.

#### Acceptance Criteria

1. FOR ALL arbitrary strings supplied as decrypted plaintext, THE ContentPayloadCodec SHALL return a decoded result without throwing.
2. IF a `shadow-invite` payload's `key` does not base64-decode to exactly 32 bytes, THEN THE ContentPayloadCodec SHALL decode it to `{ type: 'unsupported' }` and THE ShadowInviteCoordinator SHALL create no thread.
3. IF a `shadow-accept` or `shadow-decline` payload lacks a non-empty `inviteId`, THEN THE ContentPayloadCodec SHALL decode it to `{ type: 'unsupported' }`.
4. IF a `shadow-revoke` payload lacks a non-empty `inviteId` or a `threadId` of 1 to 255 characters, THEN THE ContentPayloadCodec SHALL decode it to `{ type: 'unsupported' }`.
5. WHEN the ContentPayloadCodec encodes then decodes any valid shadow control payload, THE ContentPayloadCodec SHALL produce a payload equivalent to the original (round-trip).

### Requirement 13: Control-payload interception before conversation routing

**User Story:** As a system architect, I want shadow control payloads intercepted before conversation routing, so that they never appear as ordinary messages.

#### Acceptance Criteria

1. WHEN Messaging decodes an inbound `shadow-invite`, `shadow-accept`, `shadow-decline`, or `shadow-revoke`, THE Messaging component SHALL pass it to `ShadowInviteCoordinator.handleInbound` and SHALL stop normal conversation routing when the coordinator consumes it.
2. WHEN `ShadowInviteCoordinator.handleInbound` consumes a control payload, THE ShadowInviteCoordinator SHALL emit no conversation row and SHALL pass nothing to the ConversationRegistry as a message.
3. IF an inbound payload is not a shadow control payload, THEN THE ShadowInviteCoordinator SHALL return false so Messaging continues normal routing.
4. FOR ALL inbound `shadow-revoke` payloads, THE ShadowInviteCoordinator SHALL never throw, treating an unknown or already-revoked `threadId` as a total no-op.

### Requirement 14: Device-local row-to-thread association

**User Story:** As a developer, I want a device-local association between message rows and their threadId, so that history can be purged per threadId for Clear and Revoke without changing the wire format.

#### Acceptance Criteria

1. WHEN a shadow message row is persisted, THE Row_Thread_Association SHALL record the row's `threadId` on-device.
2. WHEN "Clear shadow chat" or "Revoke shadow chat" runs for a `threadId`, THE Row_Thread_Association SHALL resolve all persisted row ids belonging to that `threadId` for KeyStore.purgeMessages.
3. THE Row_Thread_Association SHALL be a device-local addition only and SHALL NOT add any wire, envelope, or codec field.
4. THE Row_Thread_Association SHALL NOT alter the existing `MessageRow` wire representation or the frozen backend contract.

### Requirement 15: Additive local-only atomic delete on the persistence port

**User Story:** As a developer, I want an additive atomic delete on the ShadowSecretPersistence port, so that revoke can remove a thread's record, key, and alias in one all-or-nothing local write.

#### Acceptance Criteria

1. WHEN revoke deletes an invited thread, THE ShadowSecretPersistence port SHALL remove the InvitedThreadRecord, its shared `threadKey`, and any AliasEntry pointing at the `threadId` in one atomic local write.
2. IF the atomic delete fails, THEN THE ShadowSecretPersistence port SHALL abort by propagating the error, leaving nothing partial so a retry is safe.
3. THE ShadowSecretPersistence port SHALL implement the delete as a device-local persistence addition only and SHALL NOT introduce any wire, envelope, or codec change.
4. THE ShadowSecretPersistence port SHALL leave the existing `KeyStore` port shape unchanged, backing the delete with the existing encrypted store.
